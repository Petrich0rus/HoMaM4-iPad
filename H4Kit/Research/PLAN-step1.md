# Plan — Step 1 "See a map" (playable-port program, step 1 of 7) — rev 3

## Program envelope (whole "playable on iPad" program)
Goal: HoMM4 playable on iPad like on PC, controls adapted to touch. Steps: 1 see a map → 2 play a turn on the map → 3 towns → 4 combat → 5 rest of the game (objects, heroes, quests, scripts) → 6 AI → 7 saves/campaigns/sound/video. Each step = plan + user approval + slices + fresh verifier.

Shared constraints
- Code: H4Kit (Swift package: formats + game logic, testable headless on macOS) and H4App (iPadOS 17 SwiftUI app; step 1 draws the static map with the H4Kit CPU compositor in CATiledLayer tiles, Metal reserved for later steps that animate units), git repo REA → github Petrich0rus/HoMaM4-iPad (public).
- **No game material in the repo**: no game files, and no game-derived pixels or data either (renders, golden images, extracted textures/masks, map dumps). Such outputs go to the session scratchpad or to the gitignored folder `REA/out/`. Tests needing the player's data read `H4_DATA_DIR` / `H4_MAPS_DIR` and are skipped when unset (convention already used by H4Kit tests). Comparisons against references run as tests/scripts that compute images on the fly, never from committed images.
- Fidelity: formats and rules from the game data and heroes4.exe (REA/Ghidra, disassembly); inferred items are marked [I] in specs and code comments.
- Logic lives in H4Kit; the app is rendering + input.
- Touch mapping (all steps): tap = left click, long press = right click (info popup), one-finger drag = scroll, pinch = zoom, second tap on the same destination = confirm (PC double-click), Pencil/trackpad hover = PC hover, back button / two-finger tap = Esc.
- Performance target: 60 fps on an A12+/M-class iPad panning a 304×304 map; memory < 1 GB. Status: NOT verified in step 1 (no device available; only simulator measurements in 6b, where the simulator ceiling is 1.5 GB because simulator processes include host-side overhead). Owner: a device check as soon as the user runs a build on a real iPad, and at the latest the first slice of step 2.
- Commits: one commit per verified slice, pushed to origin/main (no force-push). Rollback = `git revert` of that commit.

Stops / budgets (every slice points here)
- S1 A slice is executable only when every discovery spec it depends on exists and resolves the items its acceptance needs; otherwise it is not started.
- S2 An unresolved [?] item that an acceptance criterion depends on → pause that slice and ask the user; never guess silently. Items not affecting acceptance are documented as known gaps.
- S3 Verification: at most 5 fix/re-verify passes per slice (each needing a material change); then the slice is PAUSED_VERIFICATION and reported.
- S4 A map that fails because of an undecoded format → recorded in the slice report and excluded by name; never patched around.
- S5 Budget per slice: one executor run + at most 2 follow-up fix runs; discovery: at most 2 agent runs per open question, then report to the user.

### 6a-T — Terrain render model in H4Kit (executable now)
Outcome: H4Kit computes and composites the terrain of a map level (base tiles, transitions, roads) headlessly.
Spec: scratchpad/render/SPEC_render.md §1–5 (validated by the python prototype).
Prerequisite (S1, met): FROZEN reference `scratchpad/render/render_ref.py` sha256 cf00b366b7c2da472411f3d3691094d2f41973eed91d7f32a4963d6357329703 (helpers h4lib.py 1796174468adb7dc…, masks.py 6933920f88527f09…, trans.py 701e311bf7a2fcc9…). Its docstring rules R1–R7 are normative for the Swift code (chunk function, texture naming, roads, draw order = 3 passes bases/overlays/roads in (r+c, r) order, empty-destination rule, canvas formula, RGBA output). Input = JSON from `scratchpad/render/dump` (H4Kit-based dumper of cells/overlays/roads) in render/js/ref_*.json; reference crops in render/ref6a/.
Decisions pinned for this slice (identical to render_ref.py):
- Chunk function (deterministic, documented in code + reference): chunk = 4×4 cells (cr = row>>2, cc = col>>2); h = splitmix64(0x48344D41 ^ (level<<40) ^ (cr<<20) ^ cc); ox = h % 3, oy = (h >> 8) % 3; sub-variant for (terrain t, variant v) = splitmix64(h &+ UInt64(1 + 2*t + v)) % nsub(t). Not bit-exact with the game (its LCG + neighbour pass are [?]), visually equivalent [V by prototype]. 12/13/14 use (1,1) as in the game.
- Roads: kind 0 = gravel body with the mask inverted (alpha = 15 − m), kind 1 dirt, kind 2 cobblestone, kind 3 drawn as dirt [I], road texture sub-variant 1 [I].
- Blend, per channel, integers: out = (base·(15−a) + over·a + 7) / 15; 1-bpp masks give a ∈ {0, 15}.
Scope (exclusive): new H4Kit/Sources/H4Kit/H4Transitions.swift (reader of `transition.Transitions.h4d`, reader 0x8c4f20), H4MapTerrainRender.swift (cell → base/overlay/road draw items, chunk function, CPU compositor `H4MapImage` for a cell region), h4tool command `render <Data> <map> <out.png> [--level L] [--cells r0 c0 nr nc] [--scale 1|2|4]`, tests H4KitTests/H4MapRenderTests.swift; REA/.gitignore adds `out/`. Reference: scratchpad/render/render_ref.py = copy of render_terrain.py updated to the pinned chunk function, road rule and blend (main session prepares it before execution). **H4App is not touched** (its Rendering/ copies stay until 6b).
Acceptance:
- `--scale k` (k ∈ 1,2,4,8) = full-resolution canvas (R6) downscaled by k with a k×k box average of RGBA channels (integer floor); output size = floor(W/k) × floor(H/k). Full map (no --cells): r0 = c0 = 0, nr = nc = map size, e.g. a 304 map at k=4 → 4864 × 2432.
- A1 `h4tool render-all <Data> <maps> <outdir> --scale 4` over all 105 maps × levels into REA/out/ completes in < 120 s total (release build, this Apple Silicon Mac), exit code 0, PNG sizes follow the formula, and prints `# rendered N/N levels, missing textures 0, missing masks 0`; any missing resource → non-zero exit.
- A2 Exact match (0 differing pixels, RGBA) between `h4tool render --scale 1 --cells` and render_ref.py on: "A Land without a King" level 0 cells r 80..111 × c 64..95 (403 overlays, 66 roads); "Zanfas's Challenge" level 0 cells r 200..231 × c 88..119 (383 overlays, 93 roads); "Zanfas's Challenge" level 1 (underground) cells r 152..183 × c 152..183 (225 overlays; no shipped underground crop has roads). Reference PNGs: render/ref6a/king.png, zanfas0.png, zanfas1.png.
- A3 Visual review (me + verifier) of those 3 crops: seamless coasts, roads continuous, no holes.
- A4 Unit tests (projection, mask decode 1/4 bpp, chunk function values incl. 3 fixed test vectors from render_ref.py, blend, road inversion) + swift test green (with and without data env), H4Kit iOS build green, and **H4App iOS-simulator build green with no file changed under H4App/** (`git diff --stat -- H4App` empty). New H4Kit type names must not clash with H4App's (`H4Transitions`, `H4TransitionMask`, `H4TransitionSet`, `H4TerrainLayout`): use e.g. `H4TransitionLibrary`, `H4MapTerrainRender`.
- Known gap (documented, not blocking): magic terrains 12–14 use a different tile layout [?] (visible as a cut patch in king/zanfas crops); rendered as R2 says.
Stop if: S1–S5; or A2 differences that trace to an ambiguity in SPEC_render (→ pause, report).

### 6b — Map screen in H4App (touch) — detailed
Depends on 6a-T + 6a-O (committed bac3d4f, 1914009).
Architecture decision (changes the envelope's "Metal rendering" for step 1): the static map is drawn by the verified H4Kit CPU compositor, tile by tile, displayed with UIKit UIScrollView + CATiledLayer (background tile drawing, levels of detail, native pan/inertia/pinch). Reasons: pixel-identical to the verified renderer by construction, little new code, 60 fps scrolling handled by the system. Metal stays an option for later steps (animated units) — the unfinished Metal code in H4App/H4App/Rendering/ (unused, never wired, recoverable from git 72601da) is deleted.
Scope (exclusive):
- H4Kit concurrency contract: `H4TerrainCompositor` (and the object model library) become safe for concurrent callers — every cache read/write (textures, tiles, masks, missing lists) goes through one NSLock-protected resolution step; compositing of bands stays parallel. CATiledLayer may call `pixelRect` renders from several threads on one shared compositor.
- H4Kit: `H4TerrainCompositor.render(terrain:level:region:pixelRect:scale:objects:)` — renders a pixel rectangle OF THE SAME REGION CANVAS as the 6a render of that `region` (R6 frame; cells and objects selected for the region exactly as in 6a, i.e. objects by the O2 rule of that region), at scale 1/2/4/8 (box average as in 6a-T). The app always uses region = whole map (r0 = c0 = 0, nr = nc = size); tests use the 6a crop regions; `H4MapCanvas` helper: full-map canvas size, **content rect** = bounding box of present cells (the playable rectangle, so the black margins are not shown), screen point ↔ lattice cell (inverse of R6/O1), object hit-test (object whose footprint contains a cell; topmost by draw order); tests (oracle defined in B2).
- H4App: new `MapScreen` (SwiftUI wrapper) + `TiledMapView` (UIScrollView + CATiledLayer, tile 512 px, levels of detail for scales 1…8, min zoom = whole map fits, max zoom 2×), loading progress while the scenario/terrain/objects/models load, surface/underground toggle, double-tap zoom (in at point / out to fit), long press → info popup (cell row/col, terrain name, object model + class name if any), close button; `MapDetailView` "Open map" opens it; delete Rendering/ and the placeholder MapView.swift; a launch argument `-H4AutoTour` (DEBUG only) that opens every map/level in turn, renders the visible tiles, logs `TOUR ok <map> L<l>` / `TOUR fail …` and a final `TOUR done N ok, M fail`.
Acceptance:
- B1 H4App builds for iOS device and simulator; swift test (H4Kit) green with and without data env; no game-derived file tracked.
- B2 H4Kit tile API: for each of the 3 crop regions of 6a (with objects), the mosaic of 512-px `pixelRect` renders of that region's canvas at scale 1 equals the 6a `render(region:)` of the same region at scale 1 with objects (= ref6o PNGs), 0 differing pixels; same check at scale 4 against the scale-4 region render; plus one whole-map check ("A Land without a King" L0, region = whole map, scale 4): mosaic == single whole-map render; content rect contains every present cell and no full empty row/column of tiles.
- B2c Concurrency: a data-gated test renders the B2 mosaic from ≥ 4 concurrent tasks against ONE shared compositor (fresh caches), run under Thread Sanitizer (`swift test --sanitize=thread --filter <test>`): 0 differing pixels, 0 TSan reports.
- B3 iPad simulator (iPad Pro 13" booted), game folder copied into the app's Documents/Game (as the app's own copy flow does): open "A Land without a King", "Zanfas's Challenge" (surface + underground) and "Gulf of Nayr"; screenshots look like the H4Kit renders of the same area (visual comparison by me + verifier).
- B4 gestures driven in the simulator (swipe pan, two-finger pinch, double-tap, long press on a town and on plain terrain, level toggle, close) with screenshots showing the expected effect.
- B5 `-H4AutoTour` in the simulator, with CATiledLayer's real concurrent drawing: `TOUR done 166 ok, 0 fail` (105 maps), no crash, memory < 1.5 GB (simulator ceiling, see envelope).
- B6 tile render time logged: median < 60 ms per 512-px tile at scale 1 in the simulator on this Mac (device performance not measured — noted).
Non-goals: hero selection/movement, minimap panel, animation, owner flags, armies, fog, sounds.
Stop if: S1–S5; simulator unusable (device permission refused) → report, deliver B1/B2 only.
